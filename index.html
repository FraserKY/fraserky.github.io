Imitation learning on an SO-101 arm

This page details my foray into imitation learning and ACT. I printed and built a pair of SO-101 robot arms, recorded demonstrations of a pick-and-place task, trained an ACT policy on them, and got the robot arm to complete the task autonomously. It works, as long as everything is where it was during training.

This is the write-up. It includes the things that didn't work, because those took most of the time.

1.0   TASK

Placing a cube into a box

My aims were to learn about an exciting new technology, and also potentially automate some menial tasks I find boring.. I decided it would be best to start small, so my first task was to teach a robot the arm to pick up a green cube and put it in a box. I thought this would be the best place to start learning about robot learning policies.

I started with a pencil sharpener. The policy kept stalling just short of the grasp, so I switched to a cube, which I thought would be easier to identify and could be gripped more easily. I wanted one thing working end to end before making it harder. Eventually I'd like to get to something useful, like unloading a dishwasher (although I now appreciate this is likely a very difficult problem that lots of embodied AI companies are trying to solve).

FIG. 1 — THE TRAINED POLICY RUNNING AUTONOMOUSLY, LOCAL CPU INFERENCE, AT BOTH LOOP RATES DISCUSSED IN SECTION 3.1.

The hardware setup is a pair of SO-101 arms. One is has a 'gripper' on the end (a follower), and the other a handle (a leader). I printed the parts for both and assembled them myself. To record a demonstration I move the leader by hand and the follower copies it, while two cameras (one on the follower's wrist, one overhead) record what it sees along with its joint positions.

The overhead camera used to sit on a stand in front of the follower arm. After getting poor performance from the first set of data and training, I decided an overhead view would produce a more varied output, resulting in a better trained model and inference performance. Moving it meant re-recording the dataset. I also placed some visual markers to ensure everything could be placed in the same position, to make the task more deterministic, in an attempt to get better results.

2.0   PIPELINE

From demonstrations to deployment

STAGE 1

Teleoperated demos

50 episodes recorded through the leader arm. Two camera streams at 640×480, 30fps, plus joint states.

STAGE 2

Dataset

Episodes packaged in LeRobot's dataset format and pushed to Hugging Face, so I can train from anywhere.

STAGE 3

Train ACT

Action Chunking with Transformers, 20–25k steps on a rented GPU (RunPod), checkpointed to the Hub.

STAGE 4

Deploy

Policy runs against the real arm. Local CPU inference is what I use; async and remote GPU were both tried.

ACT, or Action Chunking with Transformers is an imitation learning method used for fine robot manipluation. The transformer takes the camera and joint position data, and feeds it into a neural network. This neural network then predicts where the actuators should next position themselves. The action chunking part of the method predicts a number of future steps at a time. Predicting a number of future actions reduces compounding errors and smooths the robots movement. Temporal assembling can then be used to update / average the future actions based on a snapshot of taken a certain length into the predicted actions. It's well supported in LeRobot and trains in a couple of hours on a cheap rented GPU, which suits a 50-episode dataset.

To train an ACT model you must complete the following steps: 1. Record a number of teleoperated demonstrations of the task you want the arm to complete. 2. Train a model using the data you collect. 3. Deploy the policy onto the arm.

3.0   PROBLEMS

Two problems worth writing down

These took the longest to work out.

3.1 — CONTROL RATE

CPU inference couldn't keep up with the control loop

I don't have a local GPU, so I first ran inference on my PC's CPU . The control loop (observe, infer, act, repeat) was meant to run at 30 Hz to match the training data. It managed about 6 Hz, and the timing was inconsistent on top of that, so every cycle overran by a different amount. The arm moved in jerks and couldn't grasp properly. (although I now put this down to poor camera positioning and inconsistent training data).

My first instinct was to set the loop to a rate the CPU could achieve (--fps=6), so the timing would at least be consistent. Strangely that made things worse, not better. Leaving the loop to free-run at the default rate performed noticeably better on the arm.

My best explanation for this is that the LeRobot framework splits policy inference and motor control. The neural network may only have been returning a future actions 3 times a second, but the motor control loop is running at the 30fps rate, resulting in smoother and faster motion compared to the attempted run at 6fps.

The proper fix would be to run inference on more capable hardware, so I looked at a remote GPU. ACT predicts a chunk of actions per inference, so the robot doesn't need a new inference every timestep. LeRobot's asynchronous inference architecture splits the system into a policy_server and a robot_client talking over gRPC. I set this up on a rented RunPod GPU, which at first performed worse than running locally — I traced that to latency between my PC and the remote GPU, even after choosing one located in Europe. The client was sending full, uncompressed camera frames every cycle; JPEG-encoding them before sending cut the payload by about 90% and brought the round trip under 150 ms. Getting the async server running on Windows also took a while, including patching a broken packaging import. The motion got smoother, but the remote setup still performed worse on the arm than local CPU inference — the server logs showed the "too similar" observation filter firing hundreds of times in a row, meaning the policy was predicting almost no motion. That points at the policy rather than the network, and I haven't got to the bottom of it. So I parked the remote inference and just ran it locally.

This detour predates the overhead camera. When I set up the async gRPC architecture, the arm still had the wrist and front-facing cameras from the original setup — the move to an overhead view (section 1.0) came later, as the response to poor performance on that first dataset. So the async results above reflect the old camera setup, not the one described earlier on this page.

3.2 — CHECKPOINT CONFIG

The published checkpoint pointed at a revision that didn't exist

After training on Colab, loading the checkpoint locally failed on a pretrained_revision field baked into the model's config. It referenced a state of the repo that didn't match what was actually on the Hub. The error message wasn't much help, so I read through how LeRobot resolves checkpoints instead. The fix was editing the config directly on Hugging Face.

4.0   STATUS

It works inside the conditions it was trained on

The policy picks up the cube and puts it in the box reliably, as long as the cube, the box and the cameras are where they were during the demonstrations. Local CPU inference runs at about 2.5 Hz so the motion is jerky, but it still finishes the task, which makes me think the policy itself is fine and the speed is a separate problem.

The stall at the grasp did go away, but I changed three things at once to get there: refocused the wrist camera, moved the front camera overhead, and cleared up the background. I don't know which of those did it, and I haven't gone back to find out.

My next challenge was to get the robot to pick up a randomly placed cube and put it in the box. This is known as generalisation: getting the robot to perform the task despite changes in its environment.

I recorded a second 50 episode dataset with the cube placed randomly and trained on it for 20k steps, but that policy performed badly.

From some research online, I think it's likely that 50 episodes is too few to achieve generalisation, and I'll need to collect a lot more data.

What I'm doing next:

  • Collect more training data with the cube, placed deliberately in a number of discrete locations, and then retrain the model.
  • Invest in some more capable compute.
